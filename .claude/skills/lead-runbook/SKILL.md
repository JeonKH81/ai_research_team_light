# Lead Runbook — 팀장 실행 지침

팀장이 "지금 누구를 어떤 순서로 부를 것인가"를 결정하기 위한 지침.

## 원칙

- **필요한 연구원만 부른다.** 다섯 명을 모두 부르면 조율 비용이 산출물 개선을 넘어선다. 단계에 필요한 최소 인원을 부른다.
- **독립 작업은 병렬, 의존 작업은 순차.** 문헌 수집과 데이터 프로파일링은 동시에 가능하지만, 설계 없이 분석하면 다시 해야 한다.
- **제2검토자가 필요한 자리는 `adversarial-reviewer`(Critic)로 채운다.** 생성한 쪽이 스스로 검증하지 않는다. (정식판에는 다른 모델로 교차 검토하는 Auditor 자리가 있다).
- **생성 뒤에는 검증을 붙인다.** 각 산출물이 완성된 직후에 adversarial-reviewer를 붙인다. 마지막에 몰아서 검증하면 이미 굳어진 오류를 발견한다.
- **설치된 스킬을 먼저 찾는다.** 문헌검색·통계·집필 도구 묶음이 설치돼 있으면 그것을 쓴다(`/help` 로 확인). 없으면 연구원이 직접 한다.

## 단계별 표준 조합

| 단계 | 소집 | 순서 | 산출물 |
|------|------|------|--------|
| 착수(idea) | lit-scout, methodologist | 병렬 → 통합 | 연구 공백 확인, 연구 질문 확정 |
| 설계(protocol) | methodologist (+lit-scout 근거) | 순차 | 설계서, 변수정의, 표본수, SAP, 프로토콜 |
| 데이터(data) | data-analyst | 단독 | 프로파일링, 정제 코드, 코드북, 데이터 버전 고정 |
| 분석(analysis) | data-analyst → adversarial-reviewer | 순차 | 결과표, 그림, 재현 코드, 이중검증 리포트 |
| 집필(writing) | writer (+lit-scout 근거) → adversarial-reviewer | 순차 | 원고, 그림, 참고문헌 |
| 리뷰대응(review) | writer, data-analyst(재분석 시) → adversarial-reviewer | 순차 | 수정본, 답변서 |

## 연구 유형별 변형

각 프로젝트 카드의 `유형` 필드에 따라 세부 절차가 달라진다. 해당 파일만 읽는다:

- 체계적문헌고찰·메타분석 → `references/meta-analysis.md`
- 코호트·관찰연구 → `references/cohort.md`
- AI 모델·벤치마크 연구 → `references/ai-benchmark.md`

## 검수 기준 (팀장이 산출물을 통과시키기 전 확인)

1. 카드의 연구 질문·설계와 산출물이 일치하는가
2. 모든 수치에 출처(파일 경로 또는 인용)가 붙어 있는가
3. 계획에 없던 분석이 있다면 탐색적이라고 표시되었는가
4. 참고문헌이 검증을 거쳤는가
5. 누락·실패가 있다면 명시되었는가 — 조용히 빠진 항목이 가장 위험하다

하나라도 아니면 해당 연구원에게 되돌린다.

## 에러 핸들링

- 연구원 1회 실패 → 지시 구체화 후 재호출. 재실패 시 누락을 명시하고 진행
- 단계 순서를 건너뛰라는 요청(설계 없이 분석 등) → 위험을 설명하고 총괄팀장에게 판단을 올린다. 팀장 단독으로 건너뛰지 않는다
- 필요한 기존 스킬이 없음 → 대안 스킬을 쓰고 어떤 절차를 대체했는지 기록

## 테스트 시나리오

**정상:** 카드 유형이 meta-analysis, 단계가 protocol → `references/meta-analysis.md` 로드 → lit-scout(검색전략) + methodologist(포함기준·PRISMA 구조) 병렬 소집 → 통합 → adversarial-reviewer가 PRISMA-P 항목 대조 → 카드 갱신.

**에러:** 단계가 data인데 SAP가 없음 → 분석을 시작하지 않고 methodologist를 먼저 소집. 데이터를 본 뒤 세운 분석 계획은 사후 가설이 되어 결과의 신뢰를 잃는다.
