# Portfolio Review — 포트폴리오 점검·브리핑

연구실 전체를 한 화면에서 보고, 다음에 무엇을 할지 결정 가능한 형태로 만드는 스킬. 총괄팀장와 총괄팀장이 함께 쓴다.

## 워크플로우

### Step 1: 수집

1. `_team/registry.yaml`, `_team/portfolio.md`, `_team/decisions.md`를 읽는다.
2. 각 `projects/*/PROJECT.md`의 현재 단계·다음 마일스톤·차단 요인을 읽는다.
3. 실제 활동을 확인한다 — 카드의 기록과 파일 시스템이 어긋날 수 있다:
   ```bash
   find projects -maxdepth 2 -newermt "14 days ago" -type f | head
   ```
   카드는 "분석 중"인데 30일간 파일 변화가 없으면 그것이 진짜 상태다.

### Step 2: 판정

각 프로젝트를 세 상태 중 하나로 분류한다:

| 상태 | 기준 | 보고 방식 |
|------|------|-----------|
| 진행 | 14일 이내 활동 있음 | 다음 마일스톤과 예상 소요 |
| 정체 | 30일 이상 활동 없고 차단 요인 없음 | **왜 멈췄는지 추정과 재개 조건** |
| 차단 | 외부 의존(데이터·IRB·공저자)으로 대기 | 차단 요인과 해제에 필요한 행동 |

정체를 그냥 "진행 중"으로 적지 않는다. 정체된 프로젝트를 드러내는 것이 이 스킬의 핵심 가치다.

### Step 3: 우선순위 제안

다음 순으로 정렬해 제안한다:
1. **외부 마감**이 있는 것 (투고 마감, 학회 초록, 연구비 보고)
2. **차단 해제 효과**가 큰 것 (한 번의 결정으로 여러 단계가 풀리는 것)
3. **완성 근접도** — 90% 온 원고 하나를 끝내는 것이 새 분석 셋보다 가치가 크다
4. 나머지

우선순위 변경을 제안할 때는 근거를 붙인다. 근거 없는 재정렬은 다음 세션에 다시 뒤집힌다.

### Step 4: 브리핑 출력

```markdown
## 한 줄 요약
{연구실 전체 상태 한 문장}

## 프로젝트별
| ID | 제목 | 단계 | 상태 | 다음 할 일 | 마지막 활동 |
|----|------|------|------|-----------|------------|

## 이번에 할 일 (우선순위)
1. {프로젝트} — {행동} — {근거}

## 결정 필요
- {사용자만 정할 수 있는 것}

## 정체·차단
- {프로젝트}: {이유} → {재개 조건}
```

### Step 5: 반영

`_team/portfolio.md`를 이 결과로 갱신한다. 브리핑은 대화로 전달하되, 상태 변화는 반드시 파일에 남긴다 — 다음 세션의 시작점이 된다.

## 선택: 시각 대시보드

시각 자료는 연구실 현황판(`python3 _team/dashboard/refresh.py`)이 담당한다. 이 스킬은 텍스트 브리핑까지만 한다 — 중복 구현하지 않는다.

## 에러 핸들링

- `registry.yaml`과 실제 `projects/` 폴더가 불일치 → 불일치 목록을 보고하고 archivist에게 동기화를 요청한다. 조용히 한쪽에 맞추지 않는다.
- `PROJECT.md`에 `[확인 필요]` 항목이 있음 → "결정 필요"에 올린다.
- 프로젝트가 하나도 등록되지 않음 → `project-intake` 안내

## 테스트 시나리오

**정상:** "연구실 현황 알려줘" → registry + 카드 3개 + 파일 활동 확인 → P01 진행/P02 정체 45일/P03 차단(데이터 대기) 판정 → 우선순위 제안(P02 재개가 가장 값싼 진전) → 브리핑 출력 → portfolio.md 갱신.

**에러:** 카드는 "분석 중"인데 60일간 파일 변화 없음 → 카드를 그대로 옮겨 적지 않고 "정체"로 판정, 카드 기록과 실제의 불일치를 명시해 보고.
