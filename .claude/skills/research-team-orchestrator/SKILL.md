# Research Team Orchestrator

AI Research Team의 계층형 에이전트 조직을 조율해 연구 산출물을 만드는 통합 스킬.

## 실행 모드: 하이브리드 (계층적 위임)

| 단계 | 모드 | 이유 |
|------|------|------|
| 사용자 ⇄ 총괄팀장 ─┬─→ 팀장 세션 (P01·P02·…) ─→ 연구원 풀      [실행 라인]
                    ├─→ ideation-lead ─→ idea-generator            [발굴 라인]
                    │                    gap-analyst
                    │                    (+lit-scout, methodologist 공유)
                    └─→ archivist

  **총괄팀장과 팀장은 소환하는 에이전트가 아니다 — 세션이 맡는 자리다.**
  연구실 뿌리에서 열린 창이 총괄팀장, 프로젝트 폴더에서 열린 창이 그 팀의 팀장이다.
  정의는 `_team/roles/총괄팀장.md` · `_team/roles/팀장.md`.
  실제로 소환하는 것은 아래 표의 연구원들뿐이다.
  총괄팀장이 정기 랩미팅을 주재해 양 라인을 함께 검토한다
```

**소환할 수 있는 연구원** (총괄팀장·팀장은 여기 없다 — 자리이지 에이전트가 아니다)

| 에이전트 | 타입 | 역할 | 주 사용 스킬 | 출력 |
|---|---|---|---|---|
| ideation-lead | general-purpose | 주제 발굴 총괄 | `topic-discovery` | `_team/ideas/I{NN}_*.md` |
| idea-generator | general-purpose | 아이디어 발산 | `topic-discovery` | `_team/ideas/_generated_*.md` |
| gap-analyst | general-purpose | 연구공백 검증·가설 | `ma-scout`, `find-cohort-gap` | 아이디어 카드의 갭 섹션 |
| lit-scout | general-purpose | 문헌 | `search-lit` 외 | `_workspace/NN_litscout_*.md` |
| methodologist | general-purpose | 설계·통계계획 | `design-study` 외 | `_workspace/NN_method_*.md` |
| data-analyst | general-purpose | 분석 | (설치된 통계 도구가 있으면) | `_workspace/NN_analysis_*` |
| writer | general-purpose | 집필 | `write-paper` 외 | `_workspace/NN_writer_*.md` |
| adversarial-reviewer | general-purpose | 검증(결함 탐색) | — | `_workspace/NN_review_*.md` |
| archivist | general-purpose | 기록·인테이크 | `project-intake` | `PROJECT.md`, digests |

모든 `Agent` 호출에 `model: "opus"`를 명시한다. 에이전트 정의는 `.claude/agents/{name}.md`에 있으며, 호출 시 해당 파일을 읽어 프롬프트에 역할을 포함시킨다.

## 워크플로우

### Phase 0: 컨텍스트 확인

1. `_team/portfolio.md`와 `_team/registry.yaml`을 읽는다.
2. 요청 대상 프로젝트를 식별한다. 사용자가 프로젝트명을 말하지 않았다면 portfolio에서 추론하고, 후보가 둘 이상이면 총괄팀장이 사용자에게 확인한다.
3. `projects/{id}/_workspace/` 존재 여부로 실행 모드를 판정한다:
   - **미존재** → 초기 실행. Phase 1로.
   - **존재 + 부분 수정 요청** → 부분 재실행. 해당 연구원만 재호출하고 지목된 산출물만 덮어쓴다.
   - **존재 + 새 입력 제공** → 새 실행. 기존 `_workspace/`를 `_workspace_{YYYYMMDD_HHMMSS}/`로 옮긴 뒤 새로 만든다.
4. 대상 프로젝트에 `PROJECT.md`가 없으면 → `project-intake` 스킬로 카드를 먼저 만든다. 카드 없이 실행하지 않는다.
5. 요청이 "무엇을 연구할까"에 해당하면 실행 라인이 아니라 **발굴 라인**이다 → `topic-discovery`로 보낸다. 정기 검토 요청이면 `lab-meeting`으로 보낸다.

## 주간 전체 실행 — 팀을 병렬로 돌린다

&ldquo;이번 주 연구 돌려&rdquo;처럼 **특정 팀을 지목하지 않은 요청**은 이 절차를 쓴다.
1인 연구실에서 총괄을 둔 이유가 여기다 — 연구자는 여러 팀을 동시에 못 보지만, 팀은 동시에 돌 수 있다.

### 1) 움직일 수 있는 팀을 가른다

`_team/registry.yaml`을 읽고 팀마다 판정한다. **기준은 하나다 — 지금 사람 결정 없이 진전이 되는가.**

| 차단의 종류 | 판정 |
|---|---|
| 없음, 또는 기계적 작업이 남음 | **돌린다** |
| 자원(코드 회수·데이터 접근) — 사람이 가져와야 함 | 돌리지 않는다 |
| 결정(설계 변경·저널 선택·채점) — 사람만 정함 | 돌리지 않는다. 대신 **결정 요청**으로 모은다 |
| 보류(onhold) | 돌리지 않는다 |

돌릴 팀이 없으면 그렇게 보고하고 끝낸다. **일을 만들지 않는다.**

### 2) 팀마다 진행한다 — 팀장을 소환하지 않는다

팀장은 소환하는 에이전트가 아니라 **그 프로젝트 폴더에서 연 창**이다. 그래서 여러 팀을 한꺼번에 "띄우는" 일은 없다. 두 길뿐이다:
- **사용자가 팀마다 창을 연다** — 총괄은 팀별로 이번 목표를 카드(`PROJECT.md` 의 '다음 마일스톤')에 적어 두고, 어느 폴더에서 창을 열지 알려 준다
- **총괄 창에서 바로 해야 하면** 총괄이 팀마다 **연구원(Scout·Planner·Analyst·Writer·Critic)을 직접 부른다.** 프롬프트에 카드의 핵심 맥락과 이번 목표를 넣고, 산출물은 `projects/{id}/_workspace/{NN}_*.md` 에 남기게 한다. 팀 사이에 의존이 없으므로 `run_in_background: true` 로 병렬 호출해도 된다

### 3) 거두고 우선순위를 매긴다 (총괄팀장)

전부 끝나면 팀별 산출물의 끝 3줄 요약(무엇을 했는가 / 무엇이 바뀌었는가 / 사람이 정할 것)만 읽는다. **원시 출력을 다 읽지 않는다.**

우선순위는 이 순서로 정한다: **외부 마감 → 차단 해제 효과 → 완성 근접도**.

### 4) 한 번에 보고한다 (총괄팀장)

브리핑은 **하나**로 합친다. 팀별로 따로 올리지 않는다.
- 무엇이 실제로 진전됐는가 (팀별 한 줄, 산출물 경로 포함)
- **사람이 정해야 할 것** — 여기가 브리핑의 본체다
- 다음 실행에서 무엇이 풀리는가

상태가 바뀐 팀은 `report.py status`로 기록한다. 팀장이 아니라 **총괄팀장이** 한다 — 여러 팀이 동시에 정본을 고치면 어긋난다.

### Phase 1: 접수 (총괄팀장)

**역할은 폴더가 정한다.** 연구실 뿌리에서 연 창이면 이 창이 총괄팀장이고 아래를 직접 한다. 프로젝트 폴더에서 연 창이면 이 창은 그 팀의 팀장이다 — 그때는 Phase 1·2 를 건너뛰고 자기 카드의 이번 목표로 Phase 3 부터 간다. 어느 쪽이든 **총괄팀장·팀장을 소환하지 않는다.**

총괄팀장이 하는 일:
1. 요청을 "프로젝트 / 단계 / 원하는 산출물"로 번역
2. 팀 범위 밖 요청은 여기서 반려하고 적합한 스킬을 안내
3. 승인 게이트 해당 여부 판정 — 해당하면 **여기서 멈추고 사용자 확인**
4. 총괄 판단으로 넘어간다

### Phase 2: 배정 (총괄팀장)

총괄팀장이 하는 일:
1. `PROJECT.md`를 읽고 이번 실행의 목표 마일스톤을 확정
2. 우선순위·중복 점검 — 다른 프로젝트의 기존 산출물로 대체 가능한 작업이 있으면 재사용을 지시
3. **팀장도 소환하지 않는다.** 두 길 중 하나다:
   - 사용자가 그 프로젝트 폴더에서 창을 열면 그 창이 팀장이 되어 실행한다(`_team/roles/팀장.md`). 총괄은 카드에 이번 목표를 적어 넘긴다
   - 총괄 창에서 바로 진행해야 하면 총괄이 **연구원(Scout·Planner·Analyst·Writer·Critic·Archivist)을 직접 부른다** — 프롬프트에 카드의 핵심 맥락(연구 질문·설계·자료 위치·이번 목표)을 넣는다
4. 프로젝트 여럿을 동시에 굴려야 하면 프로젝트마다 팀장 창을 따로 연다. 한 창이 여러 팀의 정본을 고치지 않는다

### Phase 3: 실행 (팀장 → 연구원)

**실행 방식:** 팀장이 `lead-runbook` 스킬로 연구 유형별 표준 조합을 확인하고 필요한 연구원만 소환한다.

- 독립적인 작업(문헌 수집 ∥ 데이터 프로파일링)은 병렬로 소환
- 의존이 있는 작업(설계 → 분석 → 집필)은 순차로
- 산출물은 `projects/{id}/_workspace/{NN}_{agent}_{artifact}.{ext}`에 파일로 저장하고, 다음 연구원에게는 **경로를 넘긴다** (내용 전체를 프롬프트에 복사하지 않는다 — 컨텍스트 낭비이고 원본과 어긋날 수 있다)

### Phase 4: 검증 (adversarial-reviewer)

**각 생성 산출물이 완성되는 즉시** 검증을 붙인다. 전부 끝난 뒤 한 번에 보지 않는다.

- 분석 결과 → 통계 재현 + SAP 대조
- 원고 → 수치 정합성 + 인용 실재 + 보고지침
- 치명적 지적이 나오면 해당 연구원에게 되돌려 재작업. 2회 반복해도 해소되지 않으면 팀장이 판단해 총괄팀장로 올린다.

### Phase 5: 종합과 보고

1. 팀장이 `PROJECT.md`의 현재 상태·다음 할 일·결정 이력을 갱신
2. 총괄팀장이 `_team/portfolio.md`를 갱신하고, 되돌리기 어려운 판단은 `_team/decisions.md`에 기록
3. 총괄팀장이 사용자에게 한국어로 브리핑: **결과 / 막힌 것 / 결정 필요**
4. `_workspace/`는 삭제하지 않는다 — 사후 검증과 재현에 필요하다

## 데이터 흐름

```
사용자 요청
  → 총괄팀장: 의도 정리 (+승인 게이트)
  → 총괄팀장: 카드 읽기, 목표 확정, 팀장 배정
  → 팀장: runbook 참조, 연구원 소집
      lit-scout ──┐
      methodologist ─→ data-analyst ─→ writer
                                        ↓
                          adversarial-reviewer (각 단계 직후)
  → 팀장: 검수, PROJECT.md 갱신
  → 총괄팀장: portfolio.md / decisions.md 갱신
  → 총괄팀장: 한국어 브리핑
```

전달 방식: **파일 기반**(산출물) + **메시지 기반**(지시·보고). 수치와 문서는 항상 파일로 넘긴다.

## 에러 핸들링

| 상황 | 대응 |
|------|------|
| 연구원 실패 | 지시를 구체화해 1회 재시도. 재실패 시 해당 산출물 없이 진행하되 **누락을 보고서와 카드에 명시** |
| 데이터 스키마 불일치 | 즉시 중단, 총괄팀장까지 보고. 추측 매핑 금지 |
| 연구원 간 결과 상충 | 양쪽 보존, 출처 병기, 팀장이 근거 강도를 비교해 판단 기록 |
| 인용 검증 실패 | 해당 인용을 원고에서 제거하거나 `[미검증]` 표시. 그대로 두지 않는다 |
| 프로젝트 카드 없음 | `project-intake`로 먼저 생성 |
| 승인 게이트 해당 | 실행 중단하고 총괄팀장을 통해 사용자 확인 |
| 팀 범위 밖 요청 | 총괄팀장이 반려하고 전용 스킬 안내 |

## 1인 연구실 — 제2검토자 확보

이 연구실은 연구자 1인이다. 제2검토자를 사람으로 세우기 어려우므로 **생성한 쪽이 스스로 검증하지 않게** 한다 — 산출물마다 `adversarial-reviewer`(Critic)를 한 번 통과시키고, AI가 한 판정은 논문에 그대로 밝힌다. (정식판에는 다른 모델로 교차 검토하는 Auditor 자리가 있다.)

## 팀 범위 경계

**팀이 다루는 것:** 주제 발굴(아이디어 → 갭 검증 → 가설 → 프로토콜 초안)과 연구 실행(설계 → 데이터 → 분석 → 원고 → 리뷰 → 투고). 두 라인은 정기 랩미팅에서 만난다.

**팀이 다루지 않는 것:** IRB 심의(`irb-review`), 연구비 심사(`grant-review`), 강의·발표자료 단독 제작, 임상 업무, 도구·스킬 개발. 이들은 각 전용 스킬로 직접 처리한다.

## 테스트 시나리오

**정상 흐름:** 사용자 "P01 검색전략 확정하자" → 총괄팀장이 P01/문헌/검색식 산출물로 번역 → 총괄팀장이 카드 확인 후 lit-scout + methodologist 를 직접 소환(또는 사용자가 P01 폴더에서 팀장 창을 열어 진행) → 검색식과 포함기준 산출 → adversarial-reviewer가 PRISMA 항목 대조 → 카드·포트폴리오 갱신 → 총괄팀장 브리핑.

**에러 흐름:** 사용자 "P02 분석 돌려줘" → 데이터 파일이 카드에 적힌 경로에 없음 → data-analyst가 중단 보고 → 팀장이 총괄팀장에게 차단 요인 보고 → portfolio의 `blockers`에 기록 → 총괄팀장이 "데이터 경로 확인 필요"를 결정 필요 항목으로 사용자에게 보고. 임의의 대체 데이터로 진행하지 않는다.

**승인 게이트 흐름:** 사용자 "이 폴더 팀으로 옮겨줘" → 총괄팀장이 승인 게이트로 판정 → 이동 대상·이동 후 경로·되돌리는 방법을 제시하고 사용자 확인 → 승인 후 총괄팀장이 archivist에게 이전과 세션로그 이식을 지시.
